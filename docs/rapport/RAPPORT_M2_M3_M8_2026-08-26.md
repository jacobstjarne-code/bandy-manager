## M2 — dataförlust mellan flikar (saveRevision + compare-and-swap)

**Rotorsak:** `saveSaveGame()` skrev alltid rakt över `bandy_save_<id>` utan att jämföra mot vad som faktiskt låg på disk — sista flikens skrivning vann alltid, oavsett vilken som var äldst.

**Byggt:**
- `SaveGame.revision` — monotont löpnummer. `saveSaveGame()` jämför inkommande `game.revision` mot disk; är disken längre fram avvisas skrivningen (`conflict:true`) istället för att skriva över.
- `SaveConflictModal.tsx` — ny blockerande yta, monterad route-oberoende i `AppRouter.tsx` (en konflikt kan upptäckas på vilken skärm som helst).
- `BroadcastChannel` (`saveConflictChannel.ts`) — den STALE fliken får reda på konflikten omedelbart, inte bara vid sitt eget nästa (misslyckade) sparförsök.
- **Ett andra fynd under vägen:** ett rakt `window.location.reload()` (ErrorBoundary-mönstret) hade INTE räckt för återhämtningen — Zustands egen persist-kanal (`bandy-game-store`) är en separat, o-CAS-skyddad skrivväg som en stale flik fortsätter mata på. `resolveSaveConflict()` läser nu uttryckligen den auktoritativa kopian (`loadSaveGame`) FÖRST, sätter den i store:t, och reloadar sedan.

**Verifierat i browser** (två riktiga flikar, samma IndexedDB, Playwright): flik A sparar (revision 2), flik B (stale) försöker spara → avvisas, modalen visas komplett och rätt styled, "Ladda om" hämtar korrekt A:s data (revision 2, inte B:s föråldrade kopia). Skärmdumpar tagna.

## M3 — juniorlandslaget uppdaterade fel spelare

**Rotorsak:** kortet namngav 1-2 spelare i text, men resolvern räknade om `potentialAbility > 50` på nytt vid resolveringstillfället — kunde träffa fler/andra spelare än kortet visade, och "Ej tillgänglig 2 omg" var bara text, ingen mekanik.

**Byggt:**

**Verifierat via 5 riktade tester** (send/keep-grenar, träff/icke-träff, borta/återkommen i matchsimuleringen) — matchar CLAUDE.md:s kod-verifierad-simulation-undantag (triggervillkoret, matchday 8/15 + kvalificerande ungdomstrupp, är opraktiskt att framkalla manuellt).
